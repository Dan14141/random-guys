# Random Guys

Веб-приложение, которое загружает случайные данные о людях из внешнего API
[randomdatatools.ru](https://randomdatatools.ru/developers/), хранит их в базе данных
и отображает в виде постраничной таблицы с возможностью просмотра каждого пользователя.

## Стек технологий

- **Python** + **Django 5** — основной backend-фреймворк
- **Django Templates** — серверный рендеринг HTML
- **PostgreSQL** — основная база данных
- **Gunicorn** — WSGI-сервер для production-окружения
- **pytest + pytest-django** — тестирование
- **responses** — мокирование HTTP-запросов к внешнему API в тестах
- **Docker + docker-compose** — контейнеризация

## Обоснование выбора стека

**Почему Django, а не Django REST Framework + SPA?** По заданию требуется одна
веб-страница с таблицей и формой ввода. Выбор Vue/React в этом случае избыточен:
он бы добавил отдельный фронтенд-проект, его сборку (Vite/Webpack), сложности
с CORS и `node_modules` в Docker-образе. Django Templates с серверной пагинацией
решает задачу одним инструментом, проще в развёртывании и тестировании.
Аналогично DRF не используется — REST API отдельно от страниц по заданию не нужен.

**Почему PostgreSQL?** Задание явно говорит про "базу данных", и в продакшене
для подобного приложения с потенциально огромным количеством записей разумно
использовать полноценную СУБД, а не SQLite. В тестах для скорости используется in-memory SQLite — это
автоматически переключается в `core/settings.py` при запуске под `pytest`.

**Почему `responses` для моков?** Библиотека специально создана для перехвата
HTTP-запросов библиотеки `requests`. Декоратор `@responses.activate` гарантирует,
что в тестах ни одного реального обращения к внешнему API не произойдёт.

## Архитектура

Приложение разделено на тонкие слои согласно принципу разделения ответственности:

- **`models.py`** — единственная модель `Guy` с шестью полями, требуемыми
  заданием (пол, имя, фамилия, телефон, email, адрес).
- **`services.py`** — бизнес-логика взаимодействия с внешним API. Здесь
  происходит HTTP-запрос, нормализация ответа (API возвращает dict при count=1
  и list при count>1) и bulk-вставка в БД в одной транзакции.
- **`views.py`** — тонкие view-функции: только парсинг запроса, вызов сервиса
  и рендеринг шаблона.
- **`management/commands/load_initial_guys.py`** — команда, вызываемая при
  старте контейнера для первичной загрузки 1000 человек.

Такое разделение позволяет тестировать бизнес-логику изолированно от HTTP-слоя.

## URL-маршруты

| URL | Описание |
|---|---|
| `/` | Главная страница: таблица людей + форма загрузки из API |
| `/load/` | POST: загрузить N людей из API (вызывается формой с главной) |
| `/<id>/` | Страница конкретного человека |
| `/random/` | Случайный человек, при каждом обновлении новый |
| `/admin/` | Django-админка |

## Быстрый запуск (Docker, рекомендуется)

```bash
git clone <repo-url>
cd random-guys
docker-compose up --build
```

При первом запуске контейнер автоматически:
1. Дождётся готовности PostgreSQL.
2. Применит миграции.
3. Загрузит 1000 случайных людей из API (только если БД пуста).
4. Запустит Gunicorn на порту 8000.

Приложение доступно по адресу [http://localhost:8000](http://localhost:8000).

Для остановки: `docker-compose down`. Для полной очистки данных:
`docker-compose down -v`.

## Запуск без Docker (локально)

Требуется Python 3.12+ и установленный PostgreSQL.

```bash
# 1. Клонировать и создать venv
git clone <repo-url>
cd random-guys
python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Настроить переменные окружения
cp .env.example .env
# при необходимости отредактировать .env (данные подключения к Postgres)

# 4. Создать БД в PostgreSQL
createdb randomguys

# 5. Применить миграции и загрузить начальные данные
export $(cat .env | xargs)        # подгрузить переменные окружения
python manage.py migrate
python manage.py load_initial_guys

# 6. Запустить сервер
python manage.py runserver
```

Откройте [http://localhost:8000](http://localhost:8000).

## Запуск тестов

```bash
pytest
```

Тесты используют in-memory SQLite, поэтому PostgreSQL для них не нужен.
Все обращения к внешнему API замоканы через `responses`.

Покрытые сценарии:
- модель `Guy` и маппинг данных из API;
- сервис загрузки: успех, ошибки сети, неожиданный формат, count=1;
- управляющая команда: загрузка в пустую БД, пропуск при непустой, флаг `--force`;
- views: главная страница с пагинацией, страница пользователя, 404, `/random/`
  возвращает разных людей при повторных запросах, обработка ошибок API.

## Настройки через переменные окружения

| Переменная | По умолчанию | Описание |
|---|---|---|
| `DEBUG` | `True` | Режим отладки Django |
| `SECRET_KEY` | dev-значение | Секретный ключ Django |
| `ALLOWED_HOSTS` | `*` | Разрешённые хосты (через запятую) |
| `POSTGRES_*` | см. `.env.example` | Параметры подключения к БД |
| `INITIAL_LOAD_COUNT` | `1000` | Сколько людей грузить при старте |
| `PEOPLE_PER_PAGE` | `50` | Размер страницы пагинации |
| `RANDOMDATATOOLS_URL` | официальный URL | Адрес внешнего API |
